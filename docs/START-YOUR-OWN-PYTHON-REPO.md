# Prepare your own Python project for Portainer

You can turn an ordinary Python CLI program into a Portainer-deployable project using this demo as a template.

## 1. Start with a Python script

Make sure your program can run without a graphical interface and accepts command-line options:

```sh
python experiment.py --iterations 100 --output ./results/run-001.json
```

Test it on your laptop first. Use `argparse` or another CLI parser to make parameters explicit. Design your program to exit with status 0 when it succeeds and nonzero when it fails.

## 2. Decide where files go

In this demo, `/app` holds program code and `/results` holds persistent data. Your application should write results to `/results`, **not** to `/app`, because the container filesystem is disposable.

If your project requires input datasets, talk to the lab administrator about an approved persistent storage and upload workflow. Do not package private datasets or API keys inside the image.

## 3. Add dependencies

If the project uses Python packages, create `requirements.txt` and pin or lock versions:

```text
numpy==2.1.3
```

Add these Dockerfile lines **before** copying your source code so dependency installation can be cached:

```dockerfile
COPY requirements.txt /app/requirements.txt
RUN python -m pip install --no-cache-dir -r /app/requirements.txt
```

If your code resides in another script or package, update the `COPY` command accordingly. Run it in the image using the correct full path, e.g. `/app/experiment.py`.

## 4. Reuse the Dockerfile and Compose pattern

Copy this demo's `Dockerfile`, `compose.yaml`, `compose.batch.yaml` and GitHub Actions workflow into your repository and update the source filename and program commands.

- Use `compose.yaml` when you want a container that stays running so you can open **Console** and launch arbitrary CLI commands.
- Use `compose.batch.yaml` for an experiment that runs to completion. Change `command:` to include your script and its actual CLI flags.
- Mount a named Docker volume at the output directory your program uses.
- Keep `restart: "no"` for one-off experiments so Docker doesn't automatically repeat completed jobs.

Neither Compose file publishes a network port, which is fine for command-line programs.

## 5. Publish a private image

Push your changes to the private GitHub repository's `main` branch. GitHub Actions runs tests and publishes a new GHCR image. If you copy the workflow, its image name is generated from the repository owner and name automatically.

Private image packages need GHCR registry access configured in Portainer. Ask the lab administrator if you don't have permission to configure that.

The repository itself can stay private, and the package can stay private. Check both visibility settings.

## 6. Deploy in Portainer

Choose **Stacks → Add stack → Repository**, point to your GitHub repository and set the Compose path. In **Environment variables**, add:

`CALCULATOR_IMAGE=ghcr.io/OWNER/REPO:latest`

The variable name `CALCULATOR_IMAGE` is inherited from this demo. You can rename it to `EXPERIMENT_IMAGE` in both your Compose files and Portainer settings if that's clearer.

After publishing a new image, re-pull and redeploy so your server runs the updated code. For reproducible science, prefer the immutable `sha-COMMIT_SHA` image tag generated by the workflow and record it with your results.

## 7. Make it reliable

For real experiments:

- Save intermediate checkpoints if a job might run for hours or days.
- Store exact CLI parameters, random seeds and software versions alongside each result.
- Use unique run IDs and output filenames.
- Do not save secrets to logs or commit `.env` files.
- Request appropriate CPU and RAM limits for shared hardware.
- Back up valuable results outside the server. Docker volume persistence is not a backup.

## Mini exercise

Add a `power` operation to `calculator.py` and a unit test. Push the change, check the GitHub Actions build, redeploy the container and run `python /app/calculator.py power 2 8` from Portainer Console.
